§ 01TL;DR

We give every service its own PostgreSQL role on Tiger Cloud, ration database concurrency with CONNECTION LIMIT, and pin per-service behavior — timeouts, isolation, search path — with ALTER ROLE … SET. The hosted pgBouncer honors all of this transparently. No pgbouncer.ini edits required.

Roles and per-role config replicate automatically to the HA replica via streaming WAL. For read traffic served from the HA standby, we add reader roles that are pointed at the replica endpoint — same database, different concurrency budget, different intent.

§ 02Sizing model

Tiger reserves 17 connections from max_connections — 12 superuser plus 5 Tiger ops. The session pool caps at max_connections − 17 and the transaction pool at (max_connections − 17) × 20. CONNECTION LIMIT on a role caps the backend connections pgBouncer opens for that role — which is the actual concurrency we're rationing.

Worked example, max_connections = 500:

  • Backend budget: 483
  • Reserve ~20% for admin, migrations, and burst: target sum of per-service CONNECTION LIMIT values ≤ ~385
  • Always size with the replica's max_connections in mind — primary cannot exceed replica

If we resize the instance, revisit these numbers. The configurable max for max_connections is bounded by compute size: 500 at ≤ 4 CPU / 16 GiB; 2000 at ≥ 8 CPU / 32 GiB.

§ 03Role pattern: privilege role + login role

Two layers per service. The privilege ("group") role owns the grants; the login role is what the service authenticates as. This lets us rotate credentials, run multiple processes of the same service, or split a service in two without re-granting.

-- 1. Privilege role (no LOGIN, no password)
CREATE ROLE app_wateralert_priv NOLOGIN;

-- 2. Grants on the privilege role
GRANT USAGE ON SCHEMA public TO app_wateralert_priv;
GRANT SELECT, INSERT, UPDATE ON ALL TABLES IN SCHEMA public TO app_wateralert_priv;
GRANT USAGE ON ALL SEQUENCES IN SCHEMA public TO app_wateralert_priv;

-- Future-proof: grants apply to objects created later by tsdbadmin
ALTER DEFAULT PRIVILEGES FOR ROLE tsdbadmin IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE ON TABLES TO app_wateralert_priv;
ALTER DEFAULT PRIVILEGES FOR ROLE tsdbadmin IN SCHEMA public
  GRANT USAGE ON SEQUENCES TO app_wateralert_priv;

-- 3. Login role for the service, with concurrency cap
CREATE ROLE svc_wateralert_ingest
  LOGIN
  PASSWORD '<rotate-this-via-secrets-manager>'
  CONNECTION LIMIT 80
  IN ROLE app_wateralert_priv;

Run as tsdbadmin. We aren't superuser, but tsdbadmin can create roles and assign membership, which is enough.

§ 04Per-service roles

Concrete CONNECTION LIMIT and GUC choices for the services that actually touch the-met-db. Pool mode is chosen client-side — which Tiger connection string we hand the service — not on the role.

Services in scope

Three product services hit the-met-db directly, plus a small set of utility roles for ops and migrations:

ServiceTouches the-met-dbRead/writeEndpoint

datalinkyes — external customer API integration (reads + customer-pushed ingest)read/writeprimary (writes) + replica (reads)

svc_wateralert_ingest — WaterScope Plus ingest writer Transaction pool

The hot path: sensor data lands here, gets parsed and written into hypertables. Short transactions, high throughput, no session features needed. Highest concurrency budget on the primary.

CREATE ROLE svc_wateralert_ingest
  LOGIN PASSWORD '...' CONNECTION LIMIT 80
  IN ROLE app_wateralert_priv;

ALTER ROLE svc_wateralert_ingest SET application_name TO 'wateralert-ingest';
ALTER ROLE svc_wateralert_ingest SET statement_timeout TO '30s';
ALTER ROLE svc_wateralert_ingest SET lock_timeout TO '5s';
ALTER ROLE svc_wateralert_ingest SET idle_in_transaction_session_timeout TO '60s';
ALTER ROLE svc_wateralert_ingest SET search_path TO public;

idle_in_transaction_session_timeout matters most here — a leaked open transaction pins a backend out of the pool until the timeout fires, and wateralert-backend runs on an EC2 ASG where a stuck process can hold connections indefinitely otherwise.

svc_wateralert_api — wateralert-backend frontend-facing API Transaction pool

The same Go service also serves the API behind wateralert-frontend — meter lists, charts, threshold edits, all the UI-driven reads and writes. Tighter timeouts than ingest because user latency matters.

CREATE ROLE svc_wateralert_api
  LOGIN PASSWORD '...' CONNECTION LIMIT 60
  IN ROLE app_wateralert_priv;

ALTER ROLE svc_wateralert_api SET application_name TO 'wateralert-api';
ALTER ROLE svc_wateralert_api SET statement_timeout TO '10s';
ALTER ROLE svc_wateralert_api SET lock_timeout TO '2s';
ALTER ROLE svc_wateralert_api SET idle_in_transaction_session_timeout TO '30s';

Same privilege role as ingest (app_wateralert_priv) — they're the same codebase with the same schema reach. Separate login roles give us independent budgets and clean per-traffic-shape observability in pg_stat_activity: ingest spikes shouldn't be indistinguishable from a frontend-driven traffic surge.

svc_datalink_writer — DataLink ingest path Transaction pool · Primary

Customer-pushed data lands here — external integrations POSTing meter or sensor data into Metron. Writes go to the primary. Tighter timeouts than wateralert ingest because this path is part of a customer-facing request and we'd rather surface a clear error than hold a customer connection open.

CREATE ROLE app_datalink_priv NOLOGIN;
GRANT USAGE ON SCHEMA public TO app_datalink_priv;
GRANT SELECT, INSERT, UPDATE ON ALL TABLES IN SCHEMA public TO app_datalink_priv;
GRANT USAGE ON ALL SEQUENCES IN SCHEMA public TO app_datalink_priv;
ALTER DEFAULT PRIVILEGES FOR ROLE tsdbadmin IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE ON TABLES TO app_datalink_priv;
ALTER DEFAULT PRIVILEGES FOR ROLE tsdbadmin IN SCHEMA public
  GRANT USAGE ON SEQUENCES TO app_datalink_priv;

CREATE ROLE svc_datalink_writer
  LOGIN PASSWORD '...' CONNECTION LIMIT 40
  IN ROLE app_datalink_priv;

ALTER ROLE svc_datalink_writer SET application_name TO 'datalink-writer';
ALTER ROLE svc_datalink_writer SET statement_timeout TO '15s';
ALTER ROLE svc_datalink_writer SET lock_timeout TO '3s';
ALTER ROLE svc_datalink_writer SET idle_in_transaction_session_timeout TO '30s';

The 40-connection budget is a starting estimate for customer-pushed ingest volume — revisit after measuring. The privilege role is not shared with app_wateralert_priv: DataLink writes from external integrations on customer-controlled cadence, wateralert-backend writes from our own sensor pipeline; keeping the privilege roles distinct lets the audit trail and any future grant-tightening differ between the two ingest paths.

svc_datalink_reader — DataLink customer read API Transaction pool · Replica

The customer-facing read API on the same Lambda(s). Read-only enforced at the role level so a bug in the read path can't accidentally write. Lambda concurrency can spike, but pgBouncer pools backends so a moderate CONNECTION LIMIT is fine — the limit is per-node and applies to the replica endpoint.

CREATE ROLE app_datalink_ro NOLOGIN;
GRANT USAGE ON SCHEMA public TO app_datalink_ro;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO app_datalink_ro;
ALTER DEFAULT PRIVILEGES FOR ROLE tsdbadmin IN SCHEMA public
  GRANT SELECT ON TABLES TO app_datalink_ro;

CREATE ROLE svc_datalink_reader
  LOGIN PASSWORD '...' CONNECTION LIMIT 60
  IN ROLE app_datalink_ro;

ALTER ROLE svc_datalink_reader SET application_name TO 'datalink-reader';
ALTER ROLE svc_datalink_reader SET default_transaction_read_only TO on;
ALTER ROLE svc_datalink_reader SET statement_timeout TO '10s';
ALTER ROLE svc_datalink_reader SET lock_timeout TO '2s';

DataLink's reader code path points its connection string at the replica endpoint; the role itself exists on both nodes (catalog replication, see §07) but the read path never opens it against the primary. Read-after-write flows (a customer ingesting data and then immediately reading it back) should route through the writer's primary connection — same pattern as Wellspring.

svc_wellspring_writer — Wellspring admin actions Transaction pool · Primary

Internal admin dashboard on Lambda. Writes are infrequent and small — threshold edits, customer linking, admin overrides. Low concurrency, tight timeouts.

CREATE ROLE svc_wellspring_writer
  LOGIN PASSWORD '...' CONNECTION LIMIT 20
  IN ROLE app_wellspring_priv;

ALTER ROLE svc_wellspring_writer SET application_name TO 'wellspring-writer';
ALTER ROLE svc_wellspring_writer SET statement_timeout TO '15s';
ALTER ROLE svc_wellspring_writer SET lock_timeout TO '3s';
ALTER ROLE svc_wellspring_writer SET idle_in_transaction_session_timeout TO '30s';

app_wellspring_priv grants what Wellspring's write paths actually need — SELECT/INSERT/UPDATE on the admin-relevant tables. It is not the same role as app_wateralert_priv — Wellspring shouldn't write to ingest-shaped tables, and giving each service its own privilege role keeps the grants explicit.

svc_wellspring_reader — Wellspring dashboard reads Transaction pool · Replica

Most Wellspring traffic is dashboard reads — meter lists, flow charts, property summaries. Route these at the replica to keep them off the write path. Larger pool than the writer.

CREATE ROLE app_wellspring_ro NOLOGIN;
GRANT USAGE ON SCHEMA public TO app_wellspring_ro;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO app_wellspring_ro;
ALTER DEFAULT PRIVILEGES FOR ROLE tsdbadmin IN SCHEMA public
  GRANT SELECT ON TABLES TO app_wellspring_ro;

CREATE ROLE svc_wellspring_reader
  LOGIN PASSWORD '...' CONNECTION LIMIT 30
  IN ROLE app_wellspring_ro;

ALTER ROLE svc_wellspring_reader SET application_name TO 'wellspring-reader';
ALTER ROLE svc_wellspring_reader SET default_transaction_read_only TO on;
ALTER ROLE svc_wellspring_reader SET statement_timeout TO '20s';

Wellspring reads tolerate seconds of replica lag fine — admins aren't bracketing reads around their own writes. The few flows that do (e.g. confirming an admin edit applied) should route through the writer on the primary, same pattern as §07.

svc_jobs — background / scheduled jobs Session pool · Primary

Cron-style work: retention, materialized-view refresh, ad-hoc maintenance. Often needs advisory locks or temp tables, so route through the session pool. Today this covers anything the wateralert-backend cron path runs and any future scheduled tasks (e.g. a future retention worker).

CREATE ROLE svc_jobs
  LOGIN PASSWORD '...' CONNECTION LIMIT 10
  IN ROLE app_jobs_priv;

ALTER ROLE svc_jobs SET application_name TO 'jobs';
ALTER ROLE svc_jobs SET statement_timeout TO '15min';
ALTER ROLE svc_jobs SET lock_timeout TO '30s';
ALTER ROLE svc_jobs SET idle_in_transaction_session_timeout TO '5min';

app_jobs_priv should be granted the same writes as app_wateralert_priv plus whatever DDL-adjacent operations retention needs (DELETE, hypertable management functions). Worth keeping it distinct so the audit trail clearly shows ingest vs. jobs.

svc_analytics — analytics / reporting reader Transaction pool · Replica

BI tools, ad-hoc reporting queries, occasional notebook investigation. Read-only, replica endpoint, larger work_mem because reporting queries hash and sort. Small concurrency budget — a handful of long queries is fine, a hundred is not.

CREATE ROLE app_analytics_ro NOLOGIN;
GRANT USAGE ON SCHEMA public TO app_analytics_ro;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO app_analytics_ro;
ALTER DEFAULT PRIVILEGES FOR ROLE tsdbadmin IN SCHEMA public
  GRANT SELECT ON TABLES TO app_analytics_ro;

CREATE ROLE svc_analytics
  LOGIN PASSWORD '...' CONNECTION LIMIT 8
  IN ROLE app_analytics_ro;

ALTER ROLE svc_analytics SET application_name TO 'analytics';
ALTER ROLE svc_analytics SET default_transaction_read_only TO on;
ALTER ROLE svc_analytics SET statement_timeout TO '2min';
ALTER ROLE svc_analytics SET work_mem TO '64MB';
ALTER ROLE svc_analytics SET temp_file_limit TO '4GB';
ALTER ROLE svc_analytics SET search_path TO public, reporting;

work_mem is per-sort/hash node, not per-query — bump it deliberately. temp_file_limit caps the damage a runaway query can do to replica disk.

svc_oncall_ro — break-glass operator read access Session pool · Replica

Read-only role for engineers investigating production from psql or an ad-hoc client. Replica endpoint so a heavy diagnostic query can't hurt write latency. Small concurrency, generous statement timeout, session pool because operators want \timing, \watch, and similar session features.

CREATE ROLE svc_oncall_ro
  LOGIN PASSWORD '...' CONNECTION LIMIT 4
  IN ROLE app_analytics_ro;

ALTER ROLE svc_oncall_ro SET application_name TO 'oncall';
ALTER ROLE svc_oncall_ro SET default_transaction_read_only TO on;
ALTER ROLE svc_oncall_ro SET statement_timeout TO '5min';
ALTER ROLE svc_oncall_ro SET temp_file_limit TO '2GB';

Membership in app_analytics_ro is intentional — it's the same read surface, no need to duplicate grants. The split exists for connection-budget bookkeeping and so an operator session shows up distinctly in pg_stat_activity and pgBouncer pool stats. Password rotated per incident-response policy.

svc_migrate — migration / admin tooling Session pool · Primary

Schema migrations, data backfills, ad-hoc fixes. Small pool, generous timeouts, often needs session-level features. Run as tsdbadmin in practice today (see §11), but if/when we split out a dedicated migration runner, this is the role.

CREATE ROLE svc_migrate
  LOGIN PASSWORD '...' CONNECTION LIMIT 4
  IN ROLE app_migrate_priv;

ALTER ROLE svc_migrate SET application_name TO 'migrate';
ALTER ROLE svc_migrate SET statement_timeout TO '0';           -- DDL can be long
ALTER ROLE svc_migrate SET lock_timeout TO '10s';          -- but don't wedge
ALTER ROLE svc_migrate SET idle_in_transaction_session_timeout TO '10min';

Route this one through session pool.

§ 05GUC reference

What to set per service, and why:

GUCWhy per-service
application_nameShows up in pg_stat_activity and pgBouncer stats. Free observability.
statement_timeoutCap on any single query. Different services have different tolerances.
lock_timeoutCap on waiting for a lock. Critical for user-facing services.
idle_in_transaction_session_timeoutKills leaked open transactions. Mandatory for transaction-pool services.
search_pathPin schema resolution. Avoid surprises after a new schema is added.
default_transaction_isolatione.g. repeatable read for analytics if we want snapshot stability.
default_transaction_read_onlyHard guarantee for read-only services.
work_memLarger for analytics, default for OLTP. Memory is per-operation.
temp_file_limitCap on temp file disk per session. Useful guardrail for ad-hoc readers.

Anything that isn't role-scoped — cluster-wide parameters like shared_buffers or max_connections — is set in Console → Advanced parameters, not via ALTER ROLE.

§ 06Pool mode per service

The role doesn't know or care which pool a service connects through — that's chosen by the connection string handed to each service.

  • Transaction pool (different DB name in the URL): ingestion writers, API. Default choice.
  • Session pool (different port): jobs, migrations, anything using LISTEN/NOTIFY, advisory locks held across transactions, session-scoped SET (not SET LOCAL), session-level prepared statements, temp tables outside a transaction.

If we're not sure, transaction. Flip to session only when something breaks in a specific, named way.

§ 07Primary & HA replica

Tiger's HA replica is a streaming physical replica. Everything we've configured so far — roles, grants, default privileges, per-role GUCs — replicates to the standby automatically. We don't run any of the setup on the replica directly; in fact we can't, it's read-only.

What we do have to think about is what changes when the same role is reachable from two nodes, and what shape the read-from-HA workload should take.

How role and config replication actually works

Physical replication ships WAL — every write to the catalog tables (pg_authid, pg_db_role_setting, pg_default_acl) lands on the replica in the same order. So:

  • CREATE ROLE … CONNECTION LIMIT n on the primary → identical role on the replica
  • GRANTs and default privileges → identical
  • ALTER ROLE … SET → identical, same per-session config kicks in on either node
  • ALTER ROLE … PASSWORD → identical; one set of credentials for both endpoints

So our entire §03–§04 workflow stays on the primary. The replica picks it up within typical async lag (sub-second).

CONNECTION LIMIT is per-node, not cluster-wide

This is the most important fact to internalize. CONNECTION LIMIT 60 on a role means up to 60 active backends on each node. A service that hits both nodes can hold up to 120 total backends across the cluster. This isn't a bug in our budgeting — it's a property of physical replication — but it means the per-role limit is the budget for one node, repeated.

Practical consequence When sizing, treat the primary's backend budget (max_connections − 17, minus headroom) and the replica's as separate budgets. The replica's max_connections must be ≥ the primary's, but its pool is its own. Your read workload can saturate the replica without taking anything away from primary capacity.

The lightweight read-from-HA pattern

Tiger's official guidance is to create a separate read replica set for read scaling, so the HA standby is reserved purely for failover. We're not doing that — our read volume doesn't justify the third node, and the standby is idle most of the time. The trade-offs we're accepting:

  • Failover surge. When primary fails and the standby auto-promotes, our read workload is suddenly co-resident with the write workload on a single node. Plan timeouts and retries so this is recoverable.
  • No independent sizing. A real read replica set could run smaller (cheaper) or larger (more cores) than the primary. The HA standby is matched to the primary.
  • Limited lag controls. Read replica sets expose max_standby_streaming_delay and max_standby_archive_delay for tuning query cancellation under lag pressure. Whether these are tunable on the HA replica directly is worth confirming in Console before we depend on a specific behavior.

Separate reader roles — recommended

Even though the same login role works on both endpoints, we give the read paths their own role pointed at the replica. Four reasons:

  • default_transaction_read_only = on turns an accidental write into an immediate, named error rather than a replica-side cannot execute INSERT in read-only transaction several layers down the stack.
  • Cleaner observability. pg_stat_activity and SHOW POOLS tell us at a glance which traffic is read-path vs write-path.
  • Independent concurrency budgets. A wrong connection string can't let the read role crowd out write capacity on the primary.
  • Different timeouts. Reporting reads tolerate seconds; OLTP writes don't.

Concrete example — Wellspring has a writer (primary) and a reader (replica), defined in §04 and reproduced here:

-- Writer: primary endpoint, full read-write
CREATE ROLE svc_wellspring_writer
  LOGIN PASSWORD '...' CONNECTION LIMIT 20
  IN ROLE app_wellspring_priv;
ALTER ROLE svc_wellspring_writer SET application_name TO 'wellspring-writer';
ALTER ROLE svc_wellspring_writer SET statement_timeout TO '15s';
ALTER ROLE svc_wellspring_writer SET idle_in_transaction_session_timeout TO '30s';

-- Reader: replica endpoint, read-only enforced
CREATE ROLE svc_wellspring_reader
  LOGIN PASSWORD '...' CONNECTION LIMIT 30
  IN ROLE app_wellspring_ro;
ALTER ROLE svc_wellspring_reader SET application_name TO 'wellspring-reader';
ALTER ROLE svc_wellspring_reader SET default_transaction_read_only TO on;
ALTER ROLE svc_wellspring_reader SET statement_timeout TO '20s';

Both roles exist on both nodes — they have to, the catalog replicates — but Wellspring only ever points the writer at the primary endpoint and the reader at the replica endpoint. Connection strings, not catalogs, enforce the split. DataLink follows the same writer+reader pattern (svc_datalink_writer on primary for customer-pushed ingest, svc_datalink_reader on replica for customer reads).

Lag awareness at the application layer

Async replication has typical lag well under a second, with seconds-scale spikes possible under load. So:

  • Don't read-your-write from the replica. A user who just submitted a form shouldn't be served their list view off the standby in the same request.
  • For workflows that need read-after-write semantics, route through the writer's primary connection — or, if it's a heavier read, mark the path as primary-only at the app level.
  • Reporting, dashboards, and most list/detail GETs that don't bracket a write tolerate the lag fine.
Verification on the replica SELECT pg_is_in_recovery(); returns TRUE when connected to the standby. SELECT now() − pg_last_xact_replay_timestamp(); gives an approximate replay lag.

Failover behavior

When the primary fails, Tiger promotes the standby and re-establishes a new standby. The primary and replica endpoints follow their roles, so connection strings don't need to change. What does need to be solid:

  • The app's connection pool must reconnect cleanly when a connection drops — both writer and reader.
  • During the brief period when the promoted node is serving both reads and writes, expect contention; timeouts should be short enough to surface this rather than queue indefinitely.
  • Once a new replica is up, lag may be elevated for a while as it catches up — degraded read latency, not data loss.

§ 08Verification

After applying, confirm config landed:

-- Per-role attributes
SELECT rolname, rolconnlimit, rolcanlogin
FROM pg_roles
WHERE rolname LIKE 'svc_%'
ORDER BY rolname;

-- Per-role GUCs
SELECT r.rolname, s.setconfig
FROM pg_roles r
JOIN pg_db_role_setting s ON s.setrole = r.oid
WHERE r.rolname LIKE 'svc_%'
ORDER BY r.rolname;

-- Live activity by role + app
SELECT usename, application_name, state, count(*)
FROM pg_stat_activity
WHERE usename LIKE 'svc_%'
GROUP BY usename, application_name, state
ORDER BY usename;

From the pgBouncer side:

\c pgbouncer
SHOW STATS;
SHOW POOLS;
SHOW DATABASES;

SHOW POOLS is the most useful view — it shows current backend connection counts per (database, user) pair. Sum sv_active + sv_idle + sv_used for each user and compare against the role's CONNECTION LIMIT. Run this on both the primary's pgBouncer and the replica's.

§ 09Credentials, secrets & rotation

Every svc_* login role has a password we rotate independently of schema. AWS Secrets Manager is the runtime store; 1Password is the engineer-facing source of truth; sync runs one-way (1P → ASM) via the 1Password AWS Secrets Manager integration.

Operational detail — IAM policies, vault structure, integration code, rotation runbook — lives in the companion guide tiger-cloud-secrets-management. This section covers the model and the boundaries.

Storage model

One ASM secret per login role per environment. Naming: metron/{env}/the-met-db/{role}. JSON shape:

{
  "host": "tiger-prod-primary.tigerdata.io",
  "port": 6432,
  "database": "tsdb",
  "username": "svc_wateralert_ingest",
  "password": "<rotated>"
}

The host field encodes primary-vs-replica intent, which preserves the §07 property that connection strings — not catalogs — enforce the read/write split. svc_wateralert_ingest carries the primary endpoint; svc_datalink_reader, svc_wellspring_reader, svc_analytics, and svc_oncall_ro carry the replica endpoint.

1Password as source of truth, ASM as the runtime mirror

  • One 1P vault per Tiger environment (Tiger Cloud Prod, Tiger Cloud Staging, etc.), one item per svc_* role.
  • Sync agent pushes each vault into the corresponding ASM namespace, one-way.
  • Runtime services read from ASM — low latency, IAM-scoped, no 1P dependency on the hot path.
  • Engineers reach svc_oncall_ro, svc_migrate, svc_analytics through 1P directly — no AWS round-trip needed for human-facing roles.

This keeps 1P out of the request path while still giving us a single auditable place for human credential management.

How each service reads its secret

ServiceMechanism
datalink, wellspring (Lambda)IAM on the role's secret ARN; SDK fetch at cold start, cached in module scope. The AWS Parameters and Secrets Lambda Extension is an option for hot-path latency.
wateralert-backend (EC2/ASG)Instance-profile IAM; SDK fetch at startup; refresh on auth failure.
Engineers (svc_oncall_ro, svc_migrate, svc_analytics)op read from 1P, or aws secretsmanager get-secret-value via their SSO role.

Rotation flow

Manual today; the runbook lives in §06 of the companion guide. Summary:

  1. Generate a new password.
  2. ALTER ROLE svc_x PASSWORD '<new>' against the primary as tsdbadmin.
  3. Update 1P; sync propagates to ASM.
  4. Services pick up the new value on next cold start, restart, or auth-error refresh.

PostgreSQL roles hold one password at a time, so there's a brief window where new connection attempts using the old password fail with 28P01. Client-side retry with backoff is enough to mask this for most paths. AWS Secrets Manager native rotation Lambdas can perform steps 1–3 atomically once we want zero-window rotation.

Verify before depending on it Tiger's hosted pgBouncer authenticates to PG using each role's password. Confirm in a non-prod environment whether ALTER ROLE … PASSWORD via psql-as-tsdbadmin propagates to the pgBouncer-side userlist, or whether rotations must go through the Tiger Console / API. If only the Console path updates pgBouncer, route all production rotations through it and treat psql-as-tsdbadmin as the schema-and-grants channel only.

What never goes into 1P or ASM

  • tsdbadmin password — Tiger Console only. Personal 1P items for engineers who need it, not the shared environment vault.
  • Per-engineer SSO credentials — handled by Cognito / Azure Entra, out of scope here.

We never hand tsdbadmin to a service. It's for migrations and role management only.

§ 11Lifecycle & migrations

Three pieces of a role definition, three different homes.

What goes where

Role creation and passwords — not in migrations. A CREATE ROLE … PASSWORD '…' line in a versioned migration file is a secret in git. Even with placeholders and a rotate-immediately convention, you've coupled credential rotation to deployment cadence, which is backwards. Roles are bootstrapped once per environment via an idempotent script run as tsdbadmin; passwords live in the secrets manager and rotate independently.

Grants, default privileges, and role-level GUCs — in migrations. These evolve with schema. When you add a new table, the same PR grants access on it. When you tighten statement_timeout, that's a deliberate, reviewable, reversible change. Migrations are good at exactly this. With ALTER DEFAULT PRIVILEGES set up correctly (§03), new tables auto-grant without per-table grant migrations.

CONNECTION LIMIT — in migrations, but treat as ops config. Mechanically it's just ALTER ROLE. Conceptually it's capacity planning. Keep it in migrations for the audit trail, but cross-reference §10 so nobody bumps it without updating the budget tracker.

Bootstrap script Run once per env

Idempotent — safe to re-run. Creates privilege roles and login roles with placeholder concurrency limits. Passwords come from the secrets manager via psql variable substitution.

-- db/roles/bootstrap.sql
-- Run as tsdbadmin, once per environment.
-- psql -v wateralert_ingest_pw="$WATERALERT_INGEST_PW" \
--      -v wellspring_writer_pw="$WELLSPRING_WRITER_PW" \
--      -v wellspring_reader_pw="$WELLSPRING_READER_PW" \
--      -v datalink_writer_pw="$DATALINK_WRITER_PW" \
--      -v datalink_reader_pw="$DATALINK_READER_PW" …

\set ON_ERROR_STOP on

-- Privilege roles
DO $$ BEGIN
  IF NOT EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'app_wateralert_priv') THEN
    CREATE ROLE app_wateralert_priv NOLOGIN;
  END IF;
  IF NOT EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'app_wellspring_priv') THEN
    CREATE ROLE app_wellspring_priv NOLOGIN;
  END IF;
  IF NOT EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'app_wellspring_ro') THEN
    CREATE ROLE app_wellspring_ro NOLOGIN;
  END IF;
  IF NOT EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'app_datalink_priv') THEN
    CREATE ROLE app_datalink_priv NOLOGIN;
  END IF;
  IF NOT EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'app_datalink_ro') THEN
    CREATE ROLE app_datalink_ro NOLOGIN;
  END IF;
  IF NOT EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'app_analytics_ro') THEN
    CREATE ROLE app_analytics_ro NOLOGIN;
  END IF;
  IF NOT EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'app_jobs_priv') THEN
    CREATE ROLE app_jobs_priv NOLOGIN;
  END IF;
  IF NOT EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'app_migrate_priv') THEN
    CREATE ROLE app_migrate_priv NOLOGIN;
  END IF;
END $$;

-- Login roles (passwords interpolated safely)
DO $$ BEGIN
  IF NOT EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'svc_wateralert_ingest') THEN
    EXECUTE format(
      'CREATE ROLE svc_wateralert_ingest LOGIN PASSWORD %L CONNECTION LIMIT 80 IN ROLE app_wateralert_priv',
      :'wateralert_ingest_pw'
    );
  END IF;
  IF NOT EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'svc_wellspring_writer') THEN
    EXECUTE format(
      'CREATE ROLE svc_wellspring_writer LOGIN PASSWORD %L CONNECTION LIMIT 20 IN ROLE app_wellspring_priv',
      :'wellspring_writer_pw'
    );
  END IF;
  IF NOT EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'svc_wellspring_reader') THEN
    EXECUTE format(
      'CREATE ROLE svc_wellspring_reader LOGIN PASSWORD %L CONNECTION LIMIT 30 IN ROLE app_wellspring_ro',
      :'wellspring_reader_pw'
    );
  END IF;
  IF NOT EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'svc_datalink_writer') THEN
    EXECUTE format(
      'CREATE ROLE svc_datalink_writer LOGIN PASSWORD %L CONNECTION LIMIT 40 IN ROLE app_datalink_priv',
      :'datalink_writer_pw'
    );
  END IF;
  IF NOT EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'svc_datalink_reader') THEN
    EXECUTE format(
      'CREATE ROLE svc_datalink_reader LOGIN PASSWORD %L CONNECTION LIMIT 60 IN ROLE app_datalink_ro',
      :'datalink_reader_pw'
    );
  END IF;
  -- … repeat for svc_wateralert_api, svc_jobs, svc_analytics, svc_oncall_ro, svc_migrate
END $$;

-- Default privileges so future tables grant correctly
ALTER DEFAULT PRIVILEGES FOR ROLE tsdbadmin IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE ON TABLES TO app_wateralert_priv;
ALTER DEFAULT PRIVILEGES FOR ROLE tsdbadmin IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE ON TABLES TO app_wellspring_priv;
ALTER DEFAULT PRIVILEGES FOR ROLE tsdbadmin IN SCHEMA public
  GRANT SELECT ON TABLES TO app_wellspring_ro;
ALTER DEFAULT PRIVILEGES FOR ROLE tsdbadmin IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE ON TABLES TO app_datalink_priv;
ALTER DEFAULT PRIVILEGES FOR ROLE tsdbadmin IN SCHEMA public
  GRANT SELECT ON TABLES TO app_datalink_ro;
ALTER DEFAULT PRIVILEGES FOR ROLE tsdbadmin IN SCHEMA public
  GRANT SELECT ON TABLES TO app_analytics_ro;

Example ongoing migration

A normal schema migration that also adjusts a GUC and a connection limit:

-- db/migrations/0003_tighten_api_timeouts.sql

-- Schema change
ALTER TABLE meters ADD COLUMN last_seen_at TIMESTAMPTZ;
CREATE INDEX idx_meters_last_seen_at ON meters (last_seen_at);

-- Role config — idempotent, safe to re-run
ALTER ROLE svc_wateralert_api SET statement_timeout TO '8s';
ALTER ROLE svc_wateralert_api CONNECTION LIMIT 80;  -- bumped from 60; see §10

Grants on the new index aren't needed — they follow the table.

Privilege mismatch

The normal app migration role probably doesn't have CREATEROLE and shouldn't. Two clean options:

  • Single track, run as tsdbadmin. Simplest. Concentrates risk in one role, but tsdbadmin is the only role that can do everything anyway, so the blast radius is already there.
  • Two tracks. A db/roles/ runner using tsdbadmin credentials for role bootstrap; a db/migrations/ runner using a normal migration role for schema, ongoing GRANTs, and ALTERs. The migration role needs ownership of (or CREATEROLE on) each svc_* role to ALTER it. The single-track approach avoids that hassle.

Either way, ALTER ROLE … SET and ALTER ROLE … CONNECTION LIMIT work cleanly when migrations run as tsdbadmin.

Environment divergence

Dev and staging usually want simpler role topology — one or two roles with broad permissions for fast iteration, not the production granularity. Two paths:

  • Templated bootstrap. Same script, different variables per environment. Dev gets CONNECTION LIMIT 200 on a single shared svc_dev role; prod gets the full archetype set.
  • Per-environment role files. bootstrap.prod.sql, bootstrap.dev.sql. More duplication, easier to read.

Either way, ongoing migrations in db/migrations/ reference roles that exist in every environment, even if some are stubs in dev.

Drift

Manual production changes happen — emergency password rotations, granting an engineer temporary read access for an incident. Migrations don't capture these. A periodic reconciliation check pays for itself:

SELECT rolname, rolconnlimit, rolcanlogin
FROM pg_roles
WHERE rolname LIKE 'svc_%' OR rolname LIKE 'app_%'
ORDER BY rolname;

Compare to a checked-in expected-state file. Pipe the diff into CI as an advisory failure — not blocking, since drift is sometimes intentional during incidents.

The HA replica

Migrations only run against the primary endpoint. Role and grant changes replicate to the standby via WAL — no separate apply step. The migration tool doesn't need to know the replica exists. Same is true for password rotations: change once on primary, replica picks it up.

Tooling notes

  • ORM-bundled migrations (Alembic, ActiveRecord, knex, golang-migrate, etc.) handle ALTER ROLE fine as raw SQL. If we're already running one of these, just use it.
  • Atlas has first-class role and grant support with declarative diffs. Cleanest option if we want role state to be reviewable as a plan rather than as imperative migration files.
  • Terraform cyrilgdn/postgresql provider for declarative role state. Good if we go heavy on Terraform; tradeoff is splitting schema (migrations) from roles (Terraform) into two systems with different review cadences.
Recommendation for Metron The cheapest path that doesn't paint us into a corner: idempotent bootstrap script + existing migration tool + secrets manager for passwords. Revisit if role topology gets significantly more complex.
